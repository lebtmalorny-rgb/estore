# Huawei eStor T35 на ESXi 8: настройка ВМ и диагностика запуска

**Дата проверки:** 8 ноября 2026 года.

**Образ:** `OceanStor_eStor_T35_ESXi8_EN.ova`, адаптированный из Huawei Cloud T35.

**Назначение:** инструкция для администратора ESXi, у которого есть доступ к настройкам ВМ.

Исходный архив содержит варианты T35 для Huawei Cloud и FusionCompute. Подготовленная OVA — отдельная адаптация для VMware. Официальная подтверждённая конфигурация Huawei T35 для ESXi 8 не установлена. Описанные ниже параметры опираются на исходный шаблон, состав образа и лабораторную проверку на Proxmox.

## 1. Что обнаружено

В исходном шаблоне Huawei заданы **8 vCPU и 8 ядер на сокет**, то есть **1 сокет × 8 ядер**:

```xml
<rasd:VirtualQuantity>8</rasd:VirtualQuantity>
<hw:Config hw:key="coresPerSocket" hw:value="8" ovf:required="false"/>
```

В подготовленном VMware OVF сохранено общее число `8 vCPU`, но число ядер на сокет явно не указано. Это недоработка упаковки. Для аппаратных версий ниже HW20 Broadcom указывает значение по умолчанию **1 ядро на сокет**. Поэтому после импорта ВМ могла получить топологию **8 сокетов × 1 ядро**. Фактическая топология проблемной ВМ пока неизвестна. [Документация по CPU topology](https://knowledge.broadcom.com/external/article/438023/rightsizing-virtual-machines-on-esxi-80.html)

> Первый сравнительный тест — явно установить **1 сокет × 8 ядер**. Это устраняет подтверждённое расхождение с исходным шаблоном, но ещё не является доказанным исправлением ошибки `System is not ready`.

На Proxmox исходный и адаптированный диски прошли инициализацию при топологии **1 × 8**: запустился `app_data`, завершилось включение узла, CLI перешла к запросу первого пароля. Совместимость с конкретной конфигурацией ESXi этим не доказана.

## 2. Параметры ВМ

| Параметр | Значение для проверки | Основание |
|---|---|---|
| CPU | **8 vCPU** | Исходный шаблон Huawei |
| Cores per Socket | **8** | Исходный шаблон Huawei |
| Sockets | **1** | 8 vCPU / 8 ядер на сокет |
| RAM | **16384 MiB / 16 ГиБ** | Исходный шаблон Huawei |
| CPU Limit / Memory Limit | **Unlimited** | Рекомендация для диагностического запуска |
| Firmware | **BIOS** | Исходный шаблон Huawei |
| Compatibility | **Hardware version 10 — ESXi 5.5 and later** | Параметр подготовленной OVA; поддерживается ESXi 8 |
| Guest OS | **Other Linux (64-bit)** | Параметр подготовленной OVA; внутри EulerOS с ядром 3.10 |
| SCSI controller 0 | **LSI Logic Parallel** | Вариант адаптации для VMware; в initrd есть `mptspi`, `mptbase`, `mptscsih` |
| Системный диск | **20 ГиБ, SCSI 0:0** | В адаптированном образе ожидается `/dev/sda` |
| Диск данных | **240 ГиБ, SCSI 0:1** | В адаптированном образе ожидается `/dev/sdb` |
| Network adapters | **5 × E1000** | Пять адаптеров в исходном шаблоне; тип E1000 выбран для VMware |
| Состояние NIC | **Connected**, **Connect at power on** | Подключение к лабораторным port group |
| Memory Hot Add | **Выключен** | Исходный шаблон Huawei |

**CPU Hot Add:** исходный шаблон Huawei разрешает CPU hotplug. Обязательность его отключения для T35 не установлена. Если потребуется отдельный тест с фиксированной топологией, его можно провести с CPU Hot Add off; не следует одновременно менять несколько параметров при проверке причины сбоя.

**Контроллер:** LSI Logic Parallel — настройка нашего VMware-пакета. Успешный тест адаптированного диска на Proxmox проводился с VirtIO SCSI; он не подтверждает работу VMware-контроллера. Использовать VirtIO SCSI как настройку обычной ВМ ESXi по аналогии с Proxmox не требуется.

**Диск данных:** при новом развёртывании нужен выделенный пустой диск. Штатный скрипт T35 может автоматически отформатировать его. У уже инициализированной ВМ существующий диск данных следует сохранить.

**Профиль NVMe в мастере T35** относится к эмулируемому массиву. Он не требует подключения системного VMDK через виртуальный NVMe-контроллер.

Hardware version 10 поддерживается ESXi 8. Надпись `ESXi 5.5 and later` сама по себе не является ошибкой. [Матрица совместимости](https://knowledge.broadcom.com/external/article/312100/esxiesx-hosts-and-compatible-virtual-mac.html)

Лимит памяти ниже выделенного объёма ограничивает физическую память, доступную ВМ, и может приводить к вытеснению памяти гипервизором. Поэтому для диагностического запуска предлагается `Unlimited`. Это не специальное требование Huawei к T35. [Влияние лимитов CPU и RAM](https://knowledge.broadcom.com/external/article/326270/impact-of-virtual-machine-memory-and-cpu.html)

## 3. Первая проверка: исправить только топологию CPU

1. Сохранить текущие настройки ВМ: количество CPU, Cores per Socket, RAM, лимиты, тип контроллера, адреса обоих дисков и сетевые адаптеры. Зафиксировать версию/build ESXi и модель процессора хоста.
2. Выключить **ВМ эмулятора** и убедиться, что её состояние — `Powered off`.
3. Открыть `Edit Settings → Virtual Hardware → CPU`.
4. Установить:
   - `CPU = 8`;
   - `Cores per Socket = 8`;
   - итоговое количество сокетов — `1`.
5. Сохранить настройки, снова открыть их и проверить, что значение `8` сохранилось.
6. Оставить остальные параметры прежними для этого сравнительного запуска.
7. Включить ВМ и проверить запуск по разделу 5.

Для **HW20 и новее** в vSphere Client настройка находится в `VM Options → CPU Topology`. У подготовленной OVA **HW10**, поэтому применяется прежнее расположение в разделе CPU. [Расположение Cores per Socket](https://knowledge.broadcom.com/external/article/407648)

Контрольные значения в VMX, справочно:

```ini
numvcpus = "8"
cpuid.coresPerSocket = "8"
```

Предпочтительно менять их через интерфейс управления ВМ. Broadcom также описывает ситуацию, когда ESXi Host Client записывает `coresPerSocket=1` при сохранении настроек, если параметр ранее отсутствовал. Поэтому повторная проверка после сохранения полезна. [Описание поведения Host Client](https://knowledge.broadcom.com/external/article/425838)

Если фактически уже установлено **1 × 8**, тест топологии не устраняет нового расхождения: переходить к сбору журналов, не считать CPU подтверждённой причиной.

> В лабораторной проверке T35 не завершил ACPI-выключение в отведённое время. Отправленная команда Shutdown Guest ещё не означает, что ВМ выключена. Для изменения топологии нужен подтверждённый статус `Powered off`.

## 4. Если выполняется новый импорт

1. Развернуть `OceanStor_eStor_T35_ESXi8_EN.ova` через `Deploy OVF Template` / мастер импорта OVA.
2. Выбрать datastore и сопоставить сеть `eStor-Lab` с лабораторной port group.
3. Отключить автоматический запуск после импорта.
4. Перед первым включением проверить параметры из раздела 2 и явно задать **1 сокет × 8 ядер**.
5. Убедиться, что импортированы оба диска, а диск данных выделен только этому эмулятору.
6. Пройти мастер T35: IP, маска, шлюз, серийный номер, профиль SAS/NVMe.
7. Проверить запуск по разделу 5.

Для уже существующей ВМ повторный импорт и повторная инициализация не нужны для проверки одной лишь топологии CPU.

## 5. Как проверить запуск

После включения зафиксировать время старта и дождаться инициализации. В лаборатории включение узла заняло примерно **5–6 минут** от старта ядра; это ориентир, а не гарантированный срок. Для первичного наблюдения можно выделить **10–15 минут** и затем анализировать журналы, если состояние не меняется.

Проверить три признака:

1. Процесс `app_data` присутствует и не исчезает после запуска.
2. CLI перестаёт постоянно показывать `System is not ready`. На свежем образе появляется запрос первого пароля; на настроенном — ожидается штатный вход.
3. Открывается `https://IP_ЭМУЛЯТОРА:8088/`.

HTTP-ответ и страница входа подтверждают работу веб-сервера, но не готовность всего массива. Запрос первого пароля также не заменяет дальнейшую проверку пула, LUN и доступа хоста к данным.

Если CLI остаётся в ожидании, войти в `minisystem` штатным способом и выполнить команды по отдельности:

```text
ps -C app_data
ps -C sys_app
lsscsi
free -m
cat /proc/cpuinfo
cat /proc/cmdline
```

Сохранить вывод. Если конкретная команда недоступна в ограниченной консоли, сохранить сообщение об отказе и продолжить доступными средствами. Не использовать shell-конвейеры или перенаправления как часть команд minisystem.

Интерпретация:

- Только заголовок в выводе `ps -C app_data` означает, что процесс с таким именем в момент проверки не найден.
- В `lsscsi` проверить наличие обоих дисков; соответствие размеров и SCSI-адресов проверить в настройках ВМ.
- `Start all components successfully` в `startup.log` не гарантирует успешную инициализацию запущенных дочерних процессов.
- Малый `MemTotal` в госте сам по себе не доказывает лимит ESXi. В штатной строке загрузки T35 присутствуют `cache_auto_enable=1 RATIO=3 GAP=2800M` и `crashkernel`; требуется сопоставление с параметрами резервирования памяти ядром.

## 6. Что собрать, если app_data не запускается

### Параметры ESXi и ВМ

- Версия и build ESXi, модель CPU хоста.
- Число vCPU, cores per socket, RAM, CPU/Memory Limit, состояние Hot Add.
- EVC baseline кластера/ВМ и наличие ручных CPUID masks.
- Тип контроллера, адреса и размеры обоих дисков.
- Количество NIC, их MAC и соответствующие port group.
- Время запуска и возникновения ошибки.

EVC изменяет набор возможностей CPU, видимый гостю. Однако минимальные требования этой сборки T35 к AVX/AVX2 или другим инструкциям **не установлены**. Успешный запуск на Intel Xeon E5-2680 v4 с `cpu=host` — проверенный пример, а не заявленный минимум. Изменение EVC всего кластера в эту диагностическую процедуру не входит. [EVC и совместимость CPU](https://knowledge.broadcom.com/external/article/313545/vmware-evc-and-cpu-compatibility-faq.html)

### Журналы T35

Сохранить файлы из `/OSM/log/cur_debug/`:

```text
messages
msg_sys
msg_err
message_euler
startup.log
```

Если штатная учётная запись допускает SFTP, файлы можно скачать с рабочей станции. В примере `192.0.2.10` нужно заменить адресом эмулятора; использовать действующий способ аутентификации:

```bash
sftp admin@192.0.2.10
```

В интерактивном приглашении SFTP, находясь в выбранной локальной папке для журналов:

```text
get /OSM/log/cur_debug/messages
get /OSM/log/cur_debug/msg_sys
get /OSM/log/cur_debug/msg_err
get /OSM/log/cur_debug/message_euler
get /OSM/log/cur_debug/startup.log
bye
```

Доступность SFTP зависит от состояния инициализации и учётной записи. В лаборатории этот способ позволил получить журналы до завершения процедуры первого входа.

Для сравнения успешного запуска в `msg_sys` были записи `Flow execute success, flow_id:166` от `app_data` и `Flow execute success, flow_id:212` от `sys_app`. Их наличие в текущем запуске подтверждает завершение соответствующих этапов; старые записи нужно отличать по времени.

## 7. Граница подтверждённого результата

| Проверка | Результат |
|---|---|
| Исходная топология Huawei | Подтверждена: 1 сокет × 8 ядер |
| Отсутствие coresPerSocket в подготовленном OVF | Подтверждено |
| Запуск исходного и адаптированного дисков на Proxmox | `app_data` запущен, инициализация узла завершена, CLI достигла первого запроса пароля |
| Адаптированный диск с VMware LSI Logic Parallel на ESXi | Успешная инициализация не подтверждена |
| Исправление зависания сменой топологии на ESXi | Ещё не проверено |
| FC/iSCSI multipath и Cinder Epoxy | Не проверялись в этом тесте |

Причину сбоя на конкретном ESXi пока нельзя считать установленной. При подготовке этой инструкции существующие OVF, OVA и ВМ не изменялись.
